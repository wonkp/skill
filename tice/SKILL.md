# /tice — 根据当前分支改动生成提测邮件

**用法**：`/tice`｜可选前缀参数：`/tice origin/dev` 表示基线分支

```
/tice                      # 交互确认基线后生成
/tice origin/dev           # 指定基线
```

产出：`docs/submit/YYYYMMDD-提测邮件-<功能>.md`，由 `templates/render.js`（Node，无依赖）生成，字段样例见 `templates/example-data.json`。**不要手写 Markdown，用生成器**（详细格式与字段见步骤 11）。

---

## 1. 定位仓库

1. `git rev-parse --show-toplevel` 确认在 git 仓库内；不在就反问，不要继续。
2. 取远程地址作为「后端项目地址」：`git remote get-url origin`。
3. 取当前分支：`git branch --show-current`。游离头/空分支时反问。

---

## 2. 一次性收集全部信息

**开工第一件事就是把所有需要人给的信息一次问完**，不要边做边问、更不要自己编。在对话里**一次性列出全部问题**，让用户照着逐项回复。

提问**格式**参照 `grilling`：每个问题一个 `❓` 块，块内先标题、再正文（含选项），最后一行 `➡️` 给推荐答案；问题之间用 `---` 分隔。整轮问完即停，等用户作答后再继续，不要分多轮追问。

```
❓ **Q1** - **<问题标题>**：<问题正文，可含多个选项，每选项一行>

➡️ <推荐答案 + 一句理由>

---

❓ **Q2** - **<问题标题>**：<问题正文>

➡️ <推荐答案 + 一句理由>
```

提问规则：

1. `➡️` 是推荐答案，**用户回「是 / 对 / 可以」即等于接受该推荐值**，不必逐项重述。
2. 推荐答案写「不代选」的项（对比基线、需求名称），回「是」不生效，必须明确给出值。
3. **需求信息与前端信息的每个小项都是三选一：`无` / `占位` / `填写具体内容`**——`无` 就写「无」；`占位` 就写 `{待补充：…}`；`填写具体内容` 就给实际值。用户没明确选的项，一律按 `占位` 处理，**不要自行填「无」**。

**本轮要问的全部问题（Q1–Q5 一次列完）：**

❓ **Q1** - **对比基线**：用哪个分支作为本次改动的对比基线？
- `origin/dev` — 从 dev 拉出的分支
- `origin/master` — 常规特性分支
- 其他远程分支（从 `git branch -r` 挑最近常用的补 1~2 个）

---

❓ **Q2** - **需求名称**：邮件标题《》里写什么（如「资料管理-添加学科类型和权限」）？

---

❓ **Q3** - **需求信息**：以下三项各自选 `无` / `占位` / `填写具体内容`：
- 产品负责人：无 / 占位 / 具体内容
- 需求地址：无 / 占位 / 具体内容
- 原型地址：无 / 占位 / 具体内容

➡️ 三项均按「占位」处理（回「是」即全部占位）；有具体值的请逐项写出。

---

❓ **Q4** - **前端部署信息**：以下四项各自选 `无` / `占位` / `填写具体内容`，四项都选 `无` 即视为无前端：
- 前端项目名称：`viptutorbackstage` / 无 / 占位 / 具体内容
- 前端分支名称：无 / 占位 / 具体内容
- 前端项目地址：`https://gitlab.mathplore.com/viptutor/frontend/viptutorbackstage.git` / 无 / 占位 / 具体内容
- 前端开发人员：无 / 占位 / 具体内容

➡️ 四项均按「占位」（回「是」即全部占位）；本次无前端就回「四项都无」。常用候选：项目名称 `viptutorbackstage`、项目地址为上一条 URL，确认是它时回「前端是 viptutorbackstage」。**不要自行填入项目名称与开发人员**。

---

❓ **Q5** - **代码审核**：本次是否生成代码审查报告？
- **生成** — 稍后调用 `code-review` skill
- **不生成** — 「代码审核」栏写「无」
- **已有报告** — 你给路径或内容

**可推断后回填的（不用问）**：后端项目名称与地址（从 `git remote` 取）、后端开发人员（从提交作者取）、配置文件、SQL。这些在文末「待确认」里给用户过一眼即可。

## 3. 拉取改动

取合并基点，**所有 diff 都基于 merge-base**，不要用 `base..HEAD` 的两点写法（会把基线分支自己新增的同事代码算进来）：

```bash
BASE=$(git merge-base HEAD <基线>)
git log --oneline $BASE..HEAD          # 本分支的提交
git diff --name-status $BASE...HEAD    # 改动文件清单
git diff --stat $BASE...HEAD           # 改动规模
git diff $BASE...HEAD                  # 需要上下文时按文件读，不要一次全塞进来
git log --format="%an <%ae>" $BASE..HEAD | sort -u   # 后端开发人员
```

改动为空（`git diff --name-only $BASE...HEAD` 无输出）时，直接告诉用户「当前分支相对 <基线> 无改动，无法生成提测内容」并停止。

---

## 4. 识别变更类型

逐类核对，**结论只能来自实际改动**，不许凭感觉写"无"：

| 类型 | 识别方式 |
|---|---|
| **SQL / 表结构** | `*.sql` 文件；diff 中出现 `ALTER TABLE`、`CREATE TABLE`、`DROP`、`UPDATE ... SET`、mapper XML 里的 DDL 注释；`docs/sql/` 下新增脚本 |
| **配置文件** | `application*.yml/properties`、`bootstrap*.yml`、新增 `@ConfigurationProperties` 前缀、`@Value("${...}")` 新键、`docs/config/` 下模板 |
| **接口/入口** | `*Controller.java` 的新增或改动方法（取 `@RequestMapping` + 方法路径） |
| **定时任务/MQ** | `@Scheduled`、`XxlJob`、MQ `topic`/`consumerGroup` 常量、`@RabbitListener` 等 |
| **第三方依赖** | `pom.xml` 模块/依赖变化、新的 third 包（NLS、Coze、OSS 等） |
| **前端** | 本仓库几乎不含前端。有 `*.vue`/`*.tsx`/`package.json` 改动才写；否则用步骤 2 的答案 |

---

## 5. 生成「提测内容」（基于 /pr 结果精简）

调用 `Skill` 工具执行 `pr`，让它基于同一份 diff 产出 PR 正文作为素材。

**然后只做一件事：把本次所有改动项及其影响精简地列出来（原「影响范围」的内容也在这里表述清楚，不再单列影响范围栏）。**

表述规则（严格执行）：

- **只描述「改了什么 + 影响了什么」，不解释「后端怎么实现的」**。禁止出现：状态机流转细节、CAS/Redis 闸、并发策略、异常兜底逻辑、类名、方法名、内部调用链、字段级的读写条件。
- **每条一句话**，动宾结构，用 `改动项：一句话说明` 的格式。
- **粒度要求「全而短」**：新增的接口、删除的接口、表结构变更、配置项、定时任务、第三方接入、错误码，**逐项列出**，一项不漏；但每项只写用户/测试视角能看到的东西。
- 接口写「路径 + 作用」，不写入参类型和返回结构（除非测试必须知道）。
- **删除项**单独列出并标注「已删除，无替代，调用方会 404」。
- **配置项**写明不配会怎样（一句话）。
- **定时任务**写明新增了哪些 Job 及其频率。
- **不影响的范围**明确点出哪些功能不用回归。
- **风险提示**：计费、数据丢失、不可逆操作、未压测——一条一个要点。
- 不写"优化了 XX""重构了 XX"这类空话。

示例（对照参考，输出时每条转成 `- **标签**：说明`）：

```
转写接口：新增 POST /playback/transcription/submit（按课堂提交转写）、GET /playback/transcription/status（查询各段转写状态与文本）。
巡课接口：新增 POST /playback/inspection/{clazzId}（发起巡课）、GET .../status（查状态）、GET .../result（查报告）。
表结构：edu_clazz_playback_record 新增 3 个转写字段与 1 个索引；新建 edu_clazz_playback_inspection 巡课表。
转写状态：由原「成功/进行中」两态扩展为「未转写/成功/处理中/失败」四态。
自动触发：回放记录生成后自动提交转写，仅试听班默认开启。
定时任务：新增 PlaybackTranscriptionTask、ClazzInspectionTask，均每分钟执行。
配置项：新增 playback.transcription.*、playback.inspection.*、aliyun.nls.task.*；不配置则转写/巡课功能不可用。
旧接口删除：/playback/videoTranscription、/playback/update 等 8 个 Dify 链路接口已删除，无替代，调用方会 404。
不影响范围：回放列表、下载等旧功能不受影响，无需回归。
风险提示：转写依赖阿里云 NLS 计费，未做压测。
```

长度不设上限，但每一条都必须能对应到 diff 里的实际改动。

## 6. 生成「测试范围」

**不写后端逻辑**，只列「测什么 → 预期什么」，每条一句话：

- **接口**：每个新增/变更接口的正向与异常场景，一行一条。
- **页面/功能入口**：该项改动在界面上对应的操作（若有前端）。
- **状态/数据**：可观测到的状态取值与数据变化，不解释为何如此。
- **配置**：哪些配置需要试开/关，各自的可观测差异。
- **数据校验**：执行 SQL 后用哪条查询看什么结果。
- **回归**：旧功能/被删接口需要确认的项。
- **异常**：外部依赖失败、超时、限流时的可观测表现。

禁止写 CAS、并发闸、状态机内部规则、类名方法名。测试关心的是「怎么点、看到什么」，不是「代码怎么跑」。

---

## 7. 整理「配置文件」

基于步骤 4 识别到的配置改动，集中整理本次配置项，按四类归类，**只列键名与取值/说明，不写类名方法名**：

- **Nacos 配置**（来自 `@Value`/`@ConfigurationProperties` 引用、`bootstrap*.yml`、`docs/config/` 的 Nacos 模板）：**固定用 YAML 块输出**（见下方格式要求）；
- **定时器配置**（来自 `@Scheduled` cron、`XxlJob` 配置）：任务名 / cron 或执行频率 / 开关；
- **动态线程池配置**（来自线程池 Bean 或动态线程池配置类）：线程池名 / 核心线程数 / 最大线程数 / 队列容量 / 开关；
- **其他配置**（其余新增配置键）：配置键 / 取值或说明。

配置项的取值来源优先级：仓库内 `docs/config/`、`docs/design/` 说明文档 > 代码里的默认值（`@ConfigurationProperties` 的字段初始化）> 代码引用点。**不要凭空编造 Nacos dataId 或键名**，拿不准就列出来问用户。

### Nacos 配置固定用 YAML 格式

**这是硬性格式：Nacos 子块必须输出 YAML 代码块（等宽排版 + 分层缩进 + 行内 `#` 注释），不要用 `键：值` 的内联行形式。**理由：Nacos 本身存的就是 YAML，扁平化成一行一条后用户没法直接贴进配置文件。

YAML 书写规则：

1. 子标题写 `### 【Nacos 配置】`，**紧接下一行**单独写 `dataId：xxx.yml　group：DEFAULT_GROUP`；
2. 正文是 YAML，**按真实层级缩进**（两个空格一层），不要压平；
3. 每个键后面接 `# 中文说明`，列对齐（同一块内 `#` 尽量对齐）；
4. 只写**本次新增或修改的键**，不改的键不贴，避免把整个配置中心搬进来；
5. 缺值的键用 `{待补充：…}`，**不编造**；
6. dataId 文件名跟随真实环境（研发/测试/生产各一份时，写明是哪套，或列成多个 dataId 子块）。

参考样式（生成器会包上 ` ```yaml ` 代码块）：

```yaml
playback:
  transcription:
    enabled: true                 # 关闭后转写功能不可用
    maxDurationSeconds: 3600     # 超过视为音频过长，转写失败

aliyun:
  nls:
    appKey: {待补充：NLS appKey}   # 阿里云语音识别 appKey
```

其他三类（定时器 / 动态线程池 / 其他）仍用 `- **名称**：说明` 的分条行，**不要**换成 YAML。

整块是否输出：

- **本次没有任何配置变更**：邮件「配置文件」栏直接写「无」，不输出任何【xxx】子标题；
- **有配置变更**：只输出**有内容的那几类**，每类一个【xxx】子标题；没有对应配置的类别**整块不出现**，不要写「xxx：无」。

## 8. SQL 与回滚

邮件里「SQL 脚本」一栏**必须同时给升级 SQL 和回滚 SQL**，缺一不可。

- 如果本次**没有** SQL 变更：写「无」。
- 如果从 diff 里**提取不到完整 SQL**（比如只有 mapper 改动、或脚本在别的仓库/工单里）：邮件里直接写 `{待补充：…}`，并在对话里明确告诉用户缺什么，**不要自己编 DDL**。
- 如果 SQL 在 `docs/sql/` 已有文件，读出来原样引用，别改写。

回滚推导规则：

| 升级操作 | 回滚写法 | 附加提醒 |
|---|---|---|
| `ADD COLUMN` | `DROP COLUMN` | 回滚会丢该列数据 |
| `MODIFY COLUMN` | 改回**原类型/长度/默认值/注释** | 若新数据超出旧长度，回滚会截断/失败，需先清理 |
| `CREATE TABLE` | `DROP TABLE` | 回滚丢整表 |
| `ADD INDEX` | `DROP INDEX` | — |
| `RENAME` | 反向 `RENAME` | — |
| `UPDATE ... SET` 改数据 | 先用 `CREATE TABLE xxx_bak_YYYYMMDD AS SELECT` 备份，回滚时从备份恢复 | **必须显式提示先备份** |
| `INSERT` 初始化数据 | `DELETE` 对应条件（要能唯一定位） | 主键/唯一键要写清 |
| `DROP COLUMN` / `DROP TABLE` | 回滚不可用 | 必须显著标注「不可逆，需提前备份」 |

SQL 用 ` ```sql ` 代码块输出：先写一行 `-- 升级` 再贴升级 SQL，空一行，再写 `-- 回滚` 贴回滚 SQL；块外另起一行用 `>` 引用块说明「测试环境已执行，其他环境需同步执行」。对应 `data.json` 的 `sql` 数组，**一行一条**。

## 9. 代码审核

步骤 2 已经问过是否生成，这里**直接用答案**，不再重复提问。

**选「生成」时**：调用 `Skill` 工具执行 `code-review`，参数带上步骤 2 确定的同一个基线：

```
以 <基线> 作为固定点，审查 <BASE>...HEAD 的改动
```

该 skill 会并行跑 Standards（是否符合仓库编码规范 + 代码坏味道）与 Spec（是否忠实实现需求/设计文档）两轴。spec 来源优先用仓库里的 `docs/design/*.md`（本次改动通常自带技术方案）。

拿到报告后，**只把「高风险」「中风险」项输出到「代码审核」栏**，低风险项（可读性、命名、注释、代码风格、轻微坏味道等）一律不写进邮件，最多在总数里带一句「低风险 N 项已略去」。风险分级标准：

- **高风险**：会导致数据错误、计费错误、安全问题、线上故障、不可逆操作、核心链路失效；
- **中风险**：逻辑缺陷影响部分功能、边界/异常处理缺失、潜在性能或稳定性问题；
- **低风险**：可读性、命名、注释、代码风格、轻微坏味道——**不进邮件**。

压缩成下面结构（每条写明文件:行 与问题本质；某级没有就写「无」），对应 `audit` 字段：

```
summary: 共审查 N 处改动，Standards 轴 X 项、Spec 轴 Y 项；高风险 A 项、中风险 B 项，低风险已略去。
high:    <逐条列出；无则写「无」>
mid:     <逐条列出；无则写「无」>
done:    <已修复 / 待修复 / 已知遗留，逐条对应>
```

若有未修复的**高风险**问题（会导致数据错误、计费、安全问题），必须同时写进「遗留问题」栏，并在文末「待确认」里显著提示——不能只在代码审核栏里带过。

**选「不生成」时**：「代码审核」栏写「无」。

---

## 10. 遗留问题

不额外问用户，**根据已有材料自动汇总**本次遗留问题/已知风险，来源按优先级：代码审核结果（未修复的高风险/中风险项）> PR 正文（/pr 结果里标注的已知问题）> 技术方案文档（`docs/design/` 里写明的遗留）> 代码本身（diff 里的 `TODO`/`FIXME`、临时方案、硬编码、降级开关、兼容性占位等）。

逐条列出，每条一句话：`<问题>：<影响 / 处理情况>`。**没有就写「无」**，不要硬凑。未修复的高风险项（数据错误、计费、安全问题）同时写进文末「待确认」显著提示。

## 11. 输出：Markdown

**只输出 Markdown**，不写 HTML：Markdown 能被邮件客户端渲染，也方便用户逐行改字。

**用生成器，不要手写**：

```bash
node <skill-dir>/templates/render.js <data.json> <output.md>
```

- `<skill-dir>` = `tice/` 目录绝对路径（含 `templates/render.js`）
- `data.json` 结构照 `templates/example-data.json`；写到系统临时目录（如 `$TEMP/tice-data.json`）后调用，不要拼 shell 引号，**不要写进仓库**
- 生成后告知路径，并**把全文贴到对话里**

**data.json 字段**（缺失字段按下方规则处理，不要自行编造）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `title` | string | 需求名称，《》内内容 |
| `product` / `reqUrl` / `protoUrl` | string | 产品负责人 / 需求地址 / 原型地址；缺则 `{待补充：…}` |
| `changes` | `[[标签, 说明], …]` | 提测内容，见步骤 5 |
| `tests` | `[[标签, 说明], …]` | 测试范围，见步骤 6 |
| `front` / `back` | `[[键, 值], …]` | 部署信息；无前端时 `front` 传 `[["项目名称","无"],…]` 或整块按占位处理 |
| `configs` | `[{title, dataId?, group?, yaml?:[行], items?:[[k,v]]}]` | 配置文件，见步骤 7。**Nacos 用 `yaml` 数组（按行传，格式固定）**，子标题含 nacos 时缺失 `yaml` 会告警；定时器/线程池用 `items`。**无配置变更传 `[]`** |
| `sql` | `[行, …]` | SQL 按行传（重点：一行一条，不要整段塞一个元素）；无 SQL 传 `[]` |
| `sqlNote` | string | SQL 下方提醒（回滚风险 + 执行环境） |
| `legacy` | `[[标签, 说明], …]` | 遗留问题，见步骤 10 |
| `audit` | `{summary, high, mid, done}` | 代码审核；选「不生成」时整个字段省略 |

**格式约束（已固化在生成器里，不要改）**：

1. **章节 `## `、子分组 `### `**：如 `## 提测内容`、`### 【前端】`；不嵌套超过三层
2. **条目用 `- **标签**：说明`**：无序列表，标签加粗；不用 `1.`、不用 ①②③，方便逐行改字
3. **元信息用 `- 键：值`**：产品 / 项目名称 / 分支这类键值不加粗
4. **Nacos 固定 ` ```yaml ` 块**：分层缩进 + 行内 `#` 注释，子块上方标 dataId/group
5. **SQL 固定 ` ```sql ` 块**：升级与回滚必须在同一块内
6. **SQL 下方提醒用 `> ` 引用块**：回滚风险与执行环境
7. **不用表格**：邮箱与聊天窗口里表格易变形，一律用列表

**章节顺序（不可调整）**：需求信息 → 提测内容 → 测试范围 → 部署内容 → 配置文件 → SQL 脚本 → **遗留问题 → 代码审核**

**不写页脚**：产出到「代码审核」就结束，不附公司名/姓名/职位，也不加分隔线。用户发信时由企微邮箱自动签名兜底，**不要询问也不要生成签名信息**。

## 12. 输出后自检

输出前逐条核对：

1. 步骤 2 是否**一次性问完了全部信息**（基线、需求名称、产品负责人、需求地址、原型地址、前端四项、代码审核），没有边做边问；
2. 对比基线是什么、`BASE...HEAD` 的提交是否都覆盖；
3. 有 SQL 是否**同时**有升级与回滚；回滚是否标明截断/丢数据风险与执行前提；
4. 「配置文件」是否位于 SQL 之前：无配置变更写「无」；有配置时只输出有内容的类别；**Nacos 是否为 ` ```yaml ` 块 + 下一行 dataId/group，而不是压平的 `键：值` 行**；
5. 「提测内容」是否基于 /pr 结果精简成改动项，并写清删除项 404、配置影响、不影响范围、风险提示，没有混入后端实现细节；
6. 「测试范围」是否覆盖接口/页面/状态数据/配置/数据校验/回归/异常七类，且没有实现细节；
7. 「遗留问题」是否自动生成、没有就写「无」、未修复的高风险项是否同步进了待确认；
8. 代码审核是否只输出高风险与中风险项（低风险已略去）、未修复的高风险问题是否同步进了「遗留问题」；
9. **产出校验**：`render.js` 是否打印 `sections=8 table-rows=0`（不符必须改）；章节顺序是否为「…SQL 脚本 → 遗留问题 → 代码审核」；末尾是否以「代码审核」结束、无页脚/签名/分隔线。

把待确认项集中在邮件下方用一个短列表列出（「以下信息请你确认：…」），不要散落在正文里。

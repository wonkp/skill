# 代码审查标准与判据（供 `/code-review` 命令 Standards 轴使用）

本文件是代码审查的知识库 / 判据本体。内置 `code-review` 命令的 **Standards** 轴会扫描本仓库的编码标准文档（`CODING_STANDARDS.md` / `CONTRIBUTING.md` 等），把本文件当作「标准」逐 hunk 判违规，并在发现里引用「文件 + 条目」。
本文件只含「怎么判代码」的判据与纪律，不含任何交付 / 通知流程（邮件、企微群、HTML 报告）。

## 0. 审查前提（口径与纪律）

- **三点 diff 口径**：`<base>...HEAD`（merge-base 起算，只看本次改动引入的）。用两点会把基线上后来合入的改动显示成「被删掉」，产生假缺陷。
- **全程只读**：只 fetch + 读 git 对象库；不在镜像里 `checkout/switch/reset/clean/stash/pull/merge`，不做 `git worktree add`。看新版本用 `git show <ref>:<path>`。
- **只判「本次差异引入或恶化」的问题**：存量问题（本次没碰的老代码）另列「观察项」，不进严重度计数，也不作为拒绝合并的理由。
- **对事不对人**：措辞按「问题 + 影响 + 建议」，不写评价性判断。
- **高危面优先**：取证顺序先高危面（SQL/DDL、鉴权与个人信息、事务与并发、金额与时长、对外契约），再其余。

## 1. 四个基本问题（每个 hunk 都问一遍）

1. **正确性**：输入为空 / 为 0 / 为负 / 超长 / 重复 / 并发到达时，这段代码给出的结果还对吗？
2. **失败方式**：出错时是快速失败、降级、还是静默吞掉继续写脏数据？有没有可观测的痕迹（日志 + traceId）？
3. **兼容性**：老数据（库里已有行）、老客户端（在网版本）、老调用方（别处仍在调）、新旧版本并存（滚动发布）还成立吗？
4. **可运维性**：出问题能不能定位、能不能关（开关/配置）、能不能回滚（代码与数据各自）？

## 2. 严重度三档折算（报告只按「高 / 中 / 低」三档计数，五级只是定档锚点）

| 档 | 归入本档的锚点 | 判据 | 典型例子 | 对合并结论的影响 |
|---|---|---|---|---|
| **高** | `Blocker` + `Critical` | 上线即坏、资损、数据不可逆错乱、越权或凭据外泄、无回滚路径；或常见路径必错、破坏在网客户端 | 新 SQL 用到的字段库里不存在（DDL 未随包）；金额用 double 且写库；查询漏租户/用户维度条件导致越权读别人数据；密钥硬编码；`@Transactional` 同类自调用导致事务不生效；接口删/改字段而前端未同步；`SimpleDateFormat` 当静态字段 | **≥1 条即「不可合并」**，改完该条须复审 |
| **中** | `Major` | 明显性能或可靠性退化：短期不炸，但会演化成事故 | 循环里查库/发 RPC（N+1）；无分页的全量加载与导出；外部调用无超时且叠加重试；吞异常后返回成功；日志按 ERROR 打正常流程；定时任务多副本重复执行；URL 等可配置项写死 | 「改后合并」（或作者明确接受并留单号 TODO） |
| **低** | `Minor` + `Nit` | 边界处理不干净、可维护性、缺日志，以及纯风格与偏好 | 魔法值散落；方法 200 行；异常信息不带业务标识；整段注释掉的老代码；导入顺序 / 命名口味 / 日志措辞 | 不阻塞，「可合并（附建议）」 |

分档纪律（写报告时逐条对）：

1. **一条问题只归一档；高 + 中 + 低 必须等于问题清单条数**——对不上就是漏计或一条被重复计。
2. 汇总处只出现「高 X · 中 Y · 低 Z（合计 N）」；锚点名（Blocker/Critical/Major/Minor/Nit）
   只写在每条问题的括号里，用来让研发分清"上线必挂"与"常见路径必错"，不作为统计口径。
3. 高 / 中之间分不清 → **归中**，并写明"补哪条信息就升级到高"（例如缺索引需要 `SHOW INDEX` 实证）。
   中 / 低之间分不清 → 归低。
4. 风格分歧一律归低。把风格抬进高档，等于让整份报告失去可信度。
5. 存量问题（本次差异没碰的）不进三档，另列「观察项」；但**本次改动让存量问题变严重**的要计入，并注明恶化前后。
6. 另开禅道单时对齐 severity：**高 = 1 致命 / 2 严重，中 = 3 一般，低 = 4 轻微**。

下面 §3 各维度里仍写 `Blocker/Critical/Major/Minor` 是为了给出**具体锚点**（判据不同），落报告时按上表折算成三档。

## 3. 分维度清单

### A. 需求一致性与改动范围

| 信号 | 判据 |
|---|---|
| 提交信息无禅道号、一个 commit 干三件事 | 要求补：commit 可追溯到单；混入的**大段格式化/重命名**要单列一条 Minor（它掩盖真实风险），必要时要求拆提交 |
| 声明只做 A，差异里出现 B 模块的 Controller/表 | 范围溢出：要求作者说明关联需求号，否则按 Major |
| 出现整段被注释掉的老实现、`TODO 临时`、调试输出（`System.out` / `printStackTrace`） | Major（临时方案上线最容易变成永久） |
| 有需求号 | 取验收标准逐条比；缺哪条验收点就写哪条未实现 |

### B. 正确性与边界

- **空值与空集合**：`Optional.get()` 不带 `isPresent`、`list.get(0)`、`map.get(k)` 直接用、`Arrays.asList(null)`、
  拆箱 `Integer` → `int`（NPE 高发）；`Objects.equals` vs `==`；字符串比较 `equals` 常量在前。
- **集合与流**：对正在遍历的集合 `remove`；`Collectors.toMap` 未给 merge 函数（重复 key 直接抛）；
  `toMap` 的 value 为 null 时抛 NPE；并行流里用非线程安全对象。
- **时间与 GMT+8**：`new Date()` / `LocalDateTime.now()` 与库里 `datetime` 的时区口径是否一致；
  跨天/跨月边界（课表、按日统计）；`SimpleDateFormat` 当静态字段（**线程不安全 → Critical**）；
  时间戳单位（秒/毫秒）混用。
- **金额、时长与课时**：`double`/`float` 参与金额或课时计算 → Blocker 候选；
  `BigDecimal` 用 `equals` 比大小、除法未给 `RoundingMode`、`setScale` 舍入方向与业务相反。
- **状态机**：新增/修改状态流转时，检查是否覆盖了所有可达状态与取消/退款/转课等等价操作；
  是否依赖调用顺序而非显式校验（并发下会双写）。
- **幂等**：写接口/MQ 消费/定时任务是否有幂等键（唯一索引、去重表、状态 CAS）；重试路径是否会重复扣减。

### C. 事务与并发

| 信号 | 判据 / 定级 |
|---|---|
| `@Transactional` 标在 private 方法、或被同类内部 `this.xxx()` 自调用 | 事务不生效 → Critical（数据一致性直接失守） |
| 未写 `rollbackFor`，方法内抛受检异常 | 默认只回滚 RuntimeException → Critical |
| 事务里做外部调用（RPC / HTTP / Redis / MQ 发送 / 文件） | 长事务占连接 + 回滚了但外部副作用已发生 → Major/Critical；发送应在事务提交后 |
| 先写库再发消息，消费方可能比提交更快 | 消费方读不到未提交数据 → Critical |
| 分布式锁：无过期、锁粒度是全局、解锁不在 `finally`、锁内再取锁 | 各自 Major 起；锁不住关键资源算 Critical |
| 共享可变字段（成员变量存用户上下文、静态 `HashMap`） | 并发下互相覆盖 → Critical |

### D. 数据层（SQL / MyBatis / DDL）

- **`${}` 拼接**：`${` 出现在用户可控位置 → **Blocker（SQL 注入）**；`ORDER BY ${sort}` 也要看是否有白名单。
- **动态条件全表扫描**：所有 `<if>` 条件都可能不成立 → 空 where 全表；`LIKE '%xx%'` 前置通配符走不了索引；
  对索引列套函数 / 隐式类型转换（字符串列传数字）导致索引失效。
  判"有没有索引"要实证：只读库 `SHOW INDEX FROM <表>` / `DESCRIBE <表>`（通道见 §5）。
- **`SELECT *`**：新增字段即改变返回结构；宽表 + 大字段（TEXT/BLOB）拖垮内存 → Major。
- **批量**：`<foreach>` 拼超大批量（MySQL `max_allowed_packet`、`IN` 列表长度）；循环单条 insert/update → Major。
- **DDL 随包**：新表/新字段是否有变更脚本、是否幂等（`IF NOT EXISTS` 或明确人工执行）、
  大表 `ALTER` 是否评估锁表时长、是否**先上 DDL 再上代码**（滚动发布期老代码会遇到新表结构）；
  新字段的 `NOT NULL` 与默认值（历史行怎么回填）；回滚脚本有没有。缺 DDL 或顺序错 → **Blocker**。
- **逻辑删除 + 唯一键**：唯一索引未含删除标记 → 删后重建撞键 → Critical。
- **跨系统误用**：两套系统都有各自库与表，SQL 打到别的系统的表是致命错误（见 §4）。

### E. 性能与容量

- 循环内查库 / 调 RPC / 读 Redis（N+1）→ Major 起，量大按 Critical。
- 无分页的列表接口、一次性 `list` 全表再内存过滤、导出用 POI 全内存写（→ 换流式/分批）→ Major/Critical。
- 深分页 `limit 1000000,20`；排序字段无索引且未 `limit`。
- 缓存：无过期时间的 key、缓存穿透（空值不缓存）、大批 key 同刻过期（无抖动）、
  更新顺序（先更 DB 再删缓存，反过来就是脏数据窗口）。
- 新系统 `pptutor-sale` 生产日志开着 DEBUG 全量 SQL（实测），新增大 SQL 的代价在这里更高 → 阈值收紧一档。
- `pptutor-report` 线上单副本（实测），报表/导出类改动要考虑内存与耗时上限。

### F. 接口契约与兼容性

- 请求/响应 DTO：**删字段、改字段名、改类型、改枚举值语义**都是破坏性变更 → Critical，除非同包同时给出兼容处理。
- 校验：新接口有没有 `@Valid`/参数校验、批量接口的 size 上限、越权的 id（只按 id 查而不校验归属 → **Blocker 级越权**）。
- 鉴权：新系统的登录态是 Sa-Token（生产日志里出现 `cn.dev33.satoken.exception.NotLoginException`），
  新控制器要按仓内既有用法核对"是否需要登录/权限"与放行白名单（具体注解名以代码为准，别照搬结论）；
  漏鉴权的新接口 → Blocker。
- 路径与网关：新增控制器的路径前缀要与服务在网关的路由约定一致（例：APP 侧 `/app-web/...`），写错表现为线上 404。
- 归属模块：`pptutor-app` 是 APP 主入口、**新接口优先写这里**；`pptutor-app-math` 只是历史老旧数学 C 端兼容包，
  把新功能写进 math 包算架构走偏 → Major 并问一句"是不是该落 app/teaching/sale"。
- 版本并存在网：C 端 APP 无法强制升级，改动要保证老版本请求仍能工作（新增可选字段优于改语义）。

### G. 安全与合规

- 硬编码密钥 / AK / 口令 / 连接串 / 测试账号 → **Blocker**；报告里只写"位置 + 类型 + 需轮换"，**取值不进报告**。
- 个人信息（手机号、身份证、微信 openid）出现在返回体、日志、导出文件里 → Critical（要脱敏/最小化）。
- 越权三板斧：按 id 直查、批量接口不校验归属、导出/统计接口不带数据权限条件 → Blocker/Critical。
- SSRF / 任意 URL 拼接、重定向参数未校验白名单；文件上传未校验类型与路径（路径穿越）→ Critical。
- 反序列化外部 JSON 到多态类型、SpEL/OGNL/模板拼接用户输入 → Critical 起。
- 加解密：`AES/ECB`、固定 IV、`md5` 存口令、随机数用 `Random` 做令牌 → Major/Critical。

### H. 可靠性与可观测

- `catch (Exception e) {}` 空实现、只 `log.warn("失败")` 不带堆栈、catch 后返回成功 → Major 起（掩盖真问题）。
- 日志级别：正常流程打 ERROR（实测线上有大量这类噪音，个别库 ERROR 里 80%+ 是噪音，会把真信号埋掉）→ Major。
- 关键链路无 traceId / 无业务标识（用户 ID 末四位或脱敏 ID）→ 事后无法定位 → Major。
- 外部调用无超时、无熔断/降级、失败即无限重试或重试叠加 → Critical/Major。
- 定时任务：多副本重复执行（是否依赖 Quartz 集群 / 分布式锁；中文线 Quartz 走 JDBC 集群持久化，表 `QRTZ_*`）、
  任务重叠执行未加 `@DisallowConcurrentExecution`、单次处理无上限（一次拉全量）、失败无告警。
- MQ：消费异常是吞还是重投（吞=消息丢失，无脑重投=风暴）、是否有死信/最大重试、顺序性依赖、重复消费幂等。
- 推送链路（中文线 `scheduletask`）：厂商按通道分表（`t_google_*` / `t_huawei_*` / `t_urora_*` + `t_push_task`），
  改触达逻辑要看**是否漏了某个通道或某类提醒**（如到课语音/迟到提醒）。

### I. 配置、依赖与构建

- 新增配置 key 有没有**默认值**；缺值时是启动即挂还是运行期 NPE（前者优于后者，但都要写明运维动作）。
- 配置里是否分环境；`bootstrap*.yml` / nacos 里出现明文凭据 → Blocker（同 G）。
- `pom.xml` 变更：新依赖的 groupId 是否来自公司私服、版本是否 SNAPSHOT（SNAPSHOT 上线 → Major）、
  scope 是否把 `test` 依赖带进运行时、是否引入冲突的传递依赖。
- **Java 语言级别**：新系统 `pptutor-cloud` = **11**，pptutor（中文）六仓 = **1.8**。
  在中文线仓里出现 `var`、`List.of/Map.of`、`Stream.toList()`、`text block`、新 `switch` 表达式 → 编译期或运行期炸，
  至少 Critical；在新系统里用 1.8 写法不算问题，但要提示可用语言新特性。
- 单仓多模块（新系统）改动落在 `pptutor-cloud-framework` / `-dependencies` 时，会波及其他模块：
  确认版本号与调用方是否一并升级，漏改算 Critical（别人编译不过或行为静默变化）。

### J. 规范与可读性（默认归**低档**：Minor / Nit）

分层（controller/facade/service/mapper）不被打穿、方法长度与圈复杂度、重复代码块、命名与实际语义不符、
魔法数字与硬编码文案、无意义注释、`import` 冗余、日志拼接用占位符而非 `+`、异常信息带上下文。
**新系统各模块的既有写法就是标准**——不确定就读同模块同类文件，不要拿个人偏好当规范。

### K. 测试与可验证性

- 有没有随改动补测试；写了测试但断言只判"不为 null"（无效测试）；核心分支（金额、状态流转、幂等）无测试 → Major。
- 若本会话可跑构建，在**非只读副本**里编译一次；没跑就在报告里写「未经编译验证」，
  **绝不为跑测试在只读镜像里生成 target/ 或改文件**。
- 给出"提测建议"：哪些场景必测（正常/边界/异常/并发/兼容老数据）、哪些数据要造、哪些日志可以验真。

### L. 发布与回滚

审查必须覆盖（哪怕结论是"无发布依赖"）：DDL/配置/代码的上线顺序、是否需要停机或低峰、
灰度与开关方案、回滚步骤（代码回滚 + 数据如何处理）、影响面通知对象（前端 / 测试 / DBA / 运维 / 客服）。
滚动发布期**新旧版本并存**（实测当日 3 个镜像版本并存是常态）→ 接口、缓存结构、消息体、DB 都要向后兼容；
"旧代码 + 新表结构"与"新代码 + 旧表结构"两种组合都要能活着。

## 4. 本仓雷区（两套系统各自的具体事实，审查时逐条对）

| 事实 | 审查动作 |
|---|---|
| 系统只有两套：**新系统** = 单仓多模块 `pptutor-cloud`（数学+大语文+英语，禅道产品 10，Java 11，日志 project `viptutor`）；**pptutor（中文）** = 六个仓 `coreservice`/`analyticservice`/`contentservice`/`marketservice`/`qualityservice`/`scheduletask`（禅道产品 11，Java 1.8） | 差异里出现跨仓跨系统的引用（包名、表名、配置 key）就是红旗。不要说"老系统/旧系统" |
| 两套系统的 Java 包**都以 `com.pptutor.` 开头**，判归属看第二段：新系统 `sale`/`teaching`/`report`/`system`/`app`/`app.math`；中文线 `coreapi`/`analytic`/`content`/`market`/`quality`/`scheduletask` | 审查时用它判"这段代码属于哪套系统"，别拿仓库名或"看着像中文"推断 |
| 表前缀：新系统 `app_ edu_ sale_ trans_ dis_ market_ sys_`；中文线清一色 `t_*`（analyticservice 另有 `at_*`，Quartz 用 `QRTZ_*`） | 看 SQL 判库归属；典型误用是把中文线课堂表 `t_class` 与新系统 `edu_clazz` 混用 → Blocker |
| 新系统「客资」在 `potential_customer`（`pptutor-sale`），"渠道"有三口径：来源途径 `source_type`、营销渠道树 `channel`/`channel_code`（`market_channel`）、页面来源 `page_source` | 涉及"渠道"统计或筛选的改动，必须确认改的是哪个口径；口径写错表现为"数字看着对但全错" → Critical |
| `dev` 与 `master` **双向分叉**（基线只认 `dev`）；分支落后 `dev` 是常态 | 三点 diff 只证明"分叉点那一刻"没问题，真正会炸的是合并那几百个提交的瞬间——在未同步的基线上出的结论一律无效。若作者分支是从 `master` 或别的 feature 拉的，要报出来 |
| 数学不是独立系统，它在 `pptutor-cloud` 内；C 端兼容包 `com.pptutor.app.math.*`（`pptutor-app-math`） | 数学相关改动落在 math 包 → 问"为什么不是 `pptutor-app`"（见 F） |
| 业务名词 ↔ 表/代码锚点以业务域映射文档为准（新系统 12 域 / 中文线各表） | 判"这张表是不是这个域的"就查文档，别猜 |

## 5. 取证手法（不改工作区的前提下把结论钉死）

| 要什么 | 怎么做 |
|---|---|
| 本次改动的新文件全文 | `git show HEAD:<path>` |
| 文件在本分支上的演进 | `git log -p --follow <base>..HEAD -- <file>` |
| 老逻辑 / 基线现状 | 在基线工作区 `grep` / 读文件（注意那是旧版本，别当新代码） |
| 改动方法的调用方 | 先 `grep` 方法名（旧版本视角），再用 `git show HEAD:<path>` 确认新签名；漏改调用方 → Critical |
| 相关文件（mapper XML、配置、DTO） | `git ls-tree -r --name-only HEAD -- <dir>` |
| 表结构与索引实证 | 只读库 `DESCRIBE <表>` / `SHOW INDEX FROM <表>` / `SELECT ... LIMIT n`；无只读库通道则写「未实证」，不要脑补库结构 |
| 同类历史缺陷 / 是否已上线 | 禅道检索 / `git log --oneline origin/dev` 看是否已合入；有通道则查，无则写「未查」 |

## 6. 常见假阳性（报出去之前先排除）

1. **"分支删了同事的功能"** → 多半是用了两点 `base..head`；改三点重看。
2. **"这段判断没了/文件里没有这个字段"** → 你在基线工作区看到了老版本；用 `git show HEAD:<path>` 重看。
3. **"新字段库里没有，必挂"** → 先确认 DDL 是否由 DBA 单独执行（脚本在别的仓/工单里），报告里写"需确认 DDL 上线时序"而不是直接 Blocker。
4. **"日志级别写错"** → 先看该类日志是否在异常分支上；本仓既有代码把跟踪信息打成 ERROR 的先例很多，按一致性判。
5. **"魔法值应提取常量"** → 同文件同模块既有用法就是标准，降级为 Nit。
6. **"这里该用批量接口"** → 先确认调用规模（配置项固定几条就不算问题）。
7. **"缺少事务"** → 单条写语句本身原子；要指出的是哪几条写必须原子，说不清就降级。
